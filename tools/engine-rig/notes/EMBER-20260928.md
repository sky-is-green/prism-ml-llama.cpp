# Ember — AMD MoE expert residency on the prism engine (2026-09-28)

**Project codename: Ember.** Our own implementation of hot-expert residency for
MoE serving on consumer AMD: host-placed expert banks get a GPU slot band, decode
routes through the slots with an LRU ensure + on-demand H2D fetch, and the graph is
otherwise unchanged. Inspired by FlashML FreeToken's published design (LRU expert
caching, bandwidth-adaptive execution); independent code — this is the llama.cpp/ggml
engine, not their Python/Triton runtime. Branch: **`engine/ember`** (formerly
`engine/moe-slot-cache`; Hivebench branch: `ember`, formerly `amd-freetoken`).

> Measurement note: the tables below are steady-state (warm, 256-token decode,
> 185-token prompt); the `pp` column is the first completion after load, which is
> cold relative to a warm PLE stream (warm multi-request prefill reaches
> ~450–530 t/s all-resident on the 125B).

## What landed

- `ggml` op `GGML_OP_MOE_CACHE_MAP` (+ `ggml/include/ggml-moe-cache.h`): per step, copy
  the routed ids to the host, map expert ids to slots (LRU eviction, host state),
  enqueue one H2D copy per missing expert row per bank on the compute stream, and
  return the mapped ids. GPU-backend only; disables CUDA graph capture for its graph.
- `llama_moe_slot_cache` (`src/llama-moe-slot-cache.{h,cpp}`): creates the slot banks.
  A layer is cacheable when its `ffn_{gate,up,down}_exps` (or fused `ffn_gate_up_exps`)
  tensors are host-resident (e.g. placed there by `-ncmoe`/`-ot`), carry data, and
  have no scales/biases. One backend buffer per device, `N` slots per bank.
- **Identity promotion**: when `N >= n_expert`, the whole bank is copied to the GPU once
  at context init and the layer is used directly with the routed ids — no map op, no
  per-step host sync, graph capture stays on, prefill runs on GPU too.
- `build_moe_ffn` routes partial layers through the slot banks when
  `n_tokens * n_expert_used <= N` (decode); larger batches (prefill) use the host bank.
- CLI/context: `--moe-slot-cache N` / `-msc N`, or `-msc auto` (fill each device's free
  memory after a 20%+512 MiB reserve; port of FreeToken's `--moe-cache-auto` policy).
- Stats: `LLAMA_MOE_SLOT_STATS=1` prints hit/fetch totals + hit rate at context exit.

Not in this cut: CPU overflow for capped fetches (the q* hybrid split), prefill
streaming for partially-cached layers, runtime VRAM reallocation, FTW.

## Diagnosis (why the cached arms trail all-resident)

- Steady-state hit rate is **~88–90%** (cold starts understate it); at ≤16 GiB of
  offload every miss is served from page cache (~50–70 MiB of disk per 256-token
  generation) and decode is within **9–15%** of all-resident.
- The residual gap is the **per-layer host round trip + lost CUDA-graph replay**
  (~4–6 ms/step at 24 cached layers): the map op synchronizes the stream, so the
  graph containing it cannot be captured.
- At 24 GiB off, the page cache thrashes (1.6–7.4 GiB of disk reads per generation)
  and decode is disk-sensitive (11.5–15.4 t/s) — still 3–4× the no-cache arm.
- Probes: a GPU kernel **cannot read unpinned mmap memory** on this box
  (`hipMemcpyAsync` from page cache is fine; kernel dereference faults with
  "Page not present"). `hipHostMalloc(8 GiB)` works and a kernel reads it at
  **~12.5 GB/s**, half the ~25 GB/s DMA copy rate. 30 GB RAM caps pinning.
- All-resident is **dispatch-bound** (~5,000 kernels/step × ~3.5 µs; see
  `BUDGET-20260928.md`) — the biggest untouched tok/s lever for every config.

## FreeToken alignment (upstream `0d652e7`, "feat(rocm): add RDNA3 and RDNA4 runtime foundation")

Their AMD foundation: a `hip_compat.h` CUDA→HIP shim, hipcc builds of their C++
kernels, ROCm detection/arch gating (`gfx1100-1201`), `--offload-arch` build flags,
a single-bank fallback for the fused index copy, PDL launches omitted on ROCm, and
Triton fallbacks where flashinfer/sgl-kernels have no ROCm builds.

Ember is ROCm-native already, so what transferred is the **policy layer**:

- **Hybrid vs offload decision** (`moe/benchbw.py`): hybrid only when the measured CPU
  MoE bandwidth exceeds ~2× the measured PCIe gather bandwidth, else fetch misses to
  the GPU. Ours: CPU expert GEMV ≈ 12 GB/s (35B) vs PCIe gather ≈ 25 GB/s → ratio
  ≈ 0.5, so the fetch-to-GPU mode implemented here is the right call on this box.
  Their overlap bench sets the hybrid fetch fraction when hybrid is indicated.
- **Cache auto-sizing** (`engine/cache_budget.py`): budget = free memory − reserve,
  greedy expert slots first, KV takes the remainder. Ported as `-msc auto`.
- **Graph-compatible ensure** (their Triton `ensure_experts` + `fast_index_copy`):
  device-side LRU/copy list so the decode graph stays capturable. Their gather reads
  pinned host banks; our probe shows unpinned mmap cannot be kernel-read here, so
  this needs a pinned staging design — open work.

## Next steps (when unshelved)

1. **Kernel-count reduction / fusion** (all configs): the budget note's candidates
   are still unfused; targets the ~5,000-kernels/step floor. Biggest headroom.
2. **Telemetry + tuning seam**: hit/fetch rate + per-tier `tok_s`/`vram_gb` through
   the server API and Hivebench `/v1/stacks/status` (currently `null`), so `-msc auto`
   and offload choices can be validated/tuned by the harness.
3. **Prefill for partially-cached layers**: first-request pp 79–186 vs 224
   all-resident (warm harness 268–307); matters for long agent contexts.
4. **Device-side ensure + pinned gather**: recovers the 9–15% and re-enables graph
   capture; costs pinned RAM (8 GiB works, 16 GiB risky on 30 GB) and ~12.5 GB/s
   gather reads.

## Reproduce

```sh
# build
cmake --build build-hip -j 12 --target llama-server

# 35B arm (one card): partial cache vs identity promotion
HIP_VISIBLE_DEVICES=1 LLAMA_MOE_SLOT_STATS=1 ./build-hip/bin/llama-server -m <35B-iq2_m.gguf> \
  -ngl 99 -cmoe -msc 64 -c 512 -np 1 -t 8

# 125B Ember config (both cards, headless first)
HIP_VISIBLE_DEVICES=1,0 LLAMA_MOE_SLOT_STATS=1 ./build-hip/bin/llama-server \
  -m ~/Desktop/work/models/qwen38-q2_0/Q2_0/Qwen3.8-Flash-Next-GSQ-RCO-Q2_0-00001-of-00002.gguf \
  -ngl 99 -ncmoe 24 -msc 256 -c 4096 -np 1 -t 8 \
  -ts 0.522,0.478 --split-mode layer -lm mmap --lazy-mode on -fa auto
```
