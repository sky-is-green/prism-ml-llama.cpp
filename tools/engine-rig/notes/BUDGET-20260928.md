# 125B decode budget + MoE expert-sum fusion (2026-09-28)

Session work: audit of the uncommitted phase-1 fusion experiments (see
`phase1/NOTES-20260928.md`), a measurement of where decode time goes, and one
new fusion (MoE expert aggregation).

## 1. Where the ~40 ms/token goes (125B, dual-resident, clean build)

Config: `-ngl 99 -ncmoe 0 -sm layer -ts 0.53,0.47 --device ROCm1,ROCm0 -c 4096
-np 1 -t 8 -lm mmap --lazy-mode on -fa auto`, 167-token prompt, 256-token greedy.

| run | tg t/s | ms/step | GPU busy card0 / card1 |
|---|---:|---:|---:|
| graphs on (default) | 24.52-24.78 | 40.8 | 54.5% / 48.9% |
| `GGML_CUDA_DISABLE_GRAPHS=1` | 22.15 | 45.1 | 49.8% / 42.1% |

Graph replay saves only ~4.3 ms/step (10.5%); with replay the GPUs are still
~50% idle. The residual idle (~20 ms/step) is GPU-side per-kernel
serialization: ~5,000 launchable nodes/step at ~3.5-4 ms/1000 nodes.
This matches `graphbench`: replay mode is only 1.16x faster than the host loop,
the fused-per-layer mode is 20x. **Kernel count is the lever; host-side and
replay-engine overheads are secondary.**

Node census (`LLAMA_GRAPH_DUMP=2`, 7,954 nodes, 48 layers): VIEW 1614 and
RESHAPE 1154 launch nothing; the ~5,000 real kernels are dominated by
ADD 1016, MUL_MAT 797, MUL 564, UNARY 510, SCALE 472, CONT 251, GET_ROWS 223,
RMS_NORM 184, CPY 162, MUL_MAT_ID 144, REPEAT 98, GLU 96.

Repeated chains worth fusing (kernels per layer):
- MoE expert aggregation: MUL + 10 VIEW + 9 ADD (9 kernels) - **fused here**
- HC mix tail: sigmoid + MUL + CONT + 3 ADD + SCALE (7 kernels) x2
- HC combine: scale + sigmoid + scale + REPEAT + MUL + ADD (6 kernels)
- `MUL_MAT + SCALE + UNARY` (4/layer), `RMS_NORM + RESHAPE + MUL` (2/layer)

## 2. MoE expert-sum fusion

`build_moe_ffn` aggregates the selected experts with one `VIEW` per expert
followed by a serial `ADD` chain (upstream keeps this to bound node count).
Kernel `moe_expert_sum_fused_f32` (mmid.cu) computes
`out[i,t] = ((down[i,0,t]*w[0,t] + down[i,1,t]*w[1,t]) + ...)` in one launch,
replacing the MUL + 9 ADDs (10 kernels -> 1 per layer, ~430 kernels/step).

Bit-exactness: the fused kernel must keep the multiply and each add rounded
separately, exactly like the two kernels it replaces. On HIP, clang contracts
`__fmul_rn` + `__fadd_rn` into FMA, so `mmid.cu` is compiled with
`-ffp-contract=off` (per-source flag in `ggml/src/ggml-hip/CMakeLists.txt`).
Verified bit-exact against the unfused GPU chain in `hc_test`
(`moe_sum` cases: 2/4/10/15 experts, several shapes).

Measured A/B on the 125B (same build, kill switch
`GGML_CUDA_NO_MOE_SUM_FUSE=1`), 256-token greedy decodes, 3 reps each:

| run | tg t/s |
|---|---|
| fusion on | 23.98 / 24.81 / 24.91 (mean 24.57) |
| fusion off | 23.50 / 24.47 / 24.17 (mean 24.05) |

~+2% decode in this A/B (expected ~+3.5% from 432 fewer kernels/step; rep noise
is +-1 t/s). The greedy reference generation is reproduced **exactly** with the
fusion (both reference prompts, including the 64-token continuation), so the
change is numerically identical end to end - the win is pure dispatch removal.
`hc_test` covers n_used = 2/4/10/15 and nt = 1/3/5/8/17/163/512, fused vs
unfused, all bit-exact.

## 3. Test-harness findings (important for future fusion work)

- `hc_test` had been executing on **CPU**: `ggml_backend_sched_reserve()` ends
  with a reset that wipes user tensor-backend assignments, so
  `ggml_backend_sched_set_tensor_backend()` must be called *after* reserve and
  *before* alloc; assigning only leaves does not seed the assignment pass.
  Every previous `hc_test` "PASS" was therefore vacuous (and the scale_silu
  crash was never reproduced there).
- The env kill switches must be read per call (not cached in a `static`) for
  in-process A/B runs; `hc_test` relies on this.
- Two real bugs were found with the now-live GPU tests:
  1. hipcc contracts `__fmul_rn` + `__fadd_rn` into FMA. Fixed by compiling
     `mmid.cu` with `-ffp-contract=off` (per-source flag for the HIP target).
  2. The scheduler can place the fused output in the same buffer as one of the
     inputs (`ffn_moe_out` reused `w`'s buffer for one shape). The shared
     `ggml_cuda_check_fusion_memory_ranges` misses this when the input is a
     leaf (`op == GGML_OP_NONE` is skipped), so the matcher has its own
     `ggml_cuda_moe_sum_input_alias` guard that never skips leaves. Latent
     issue for other fusions that read leaf inputs.
